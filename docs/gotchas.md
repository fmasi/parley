# Platform & Implementation Gotchas

Hard-won lessons from development. Referenced from [CLAUDE.md](../CLAUDE.md).

These are numbered for stable cross-referencing — new items are appended, never re-numbered.

1. `captureMicrophone` requires macOS 15.0+ (not 14.0)
2. PackageDescription `.v15` requires swift-tools-version 6.0; use `.macOS("15.0")` string syntax with 5.9
3. Mic sample rate varies by device -- auto-detect from CMSampleBuffer format description, don't hardcode
4. ScreenCaptureKit requires `.screen` output registration even for audio-only capture
5. TCC permission is granted to the host app -- when running as .app bundle this is the bundle (CFBundleIdentifier: eu.fmasi.parley); when running from Terminal it's Terminal.app
6. XPC services only work inside .app bundles -- the bare binary will get an XPC connection error
7. UNUserNotificationCenter requires a bundled app -- guarded with `Bundle.main.bundleIdentifier != nil`
8. Use `remoteObjectProxyWithErrorHandler` for XPC calls to prevent continuation leaks
9. MenuBarExtra with `.menu` style cannot present sheets -- use NSPanel via window controllers
10. Calendar access requires `NSCalendarsUsageDescription` in Info.plist and `requestFullAccessToEvents()` at launch
11. Screen Recording has no requestAuthorization API -- use `CGPreflightScreenCaptureAccess()` to check (no prompt) and `CGRequestScreenCaptureAccess()` to request (opens System Settings)
12. All required permissions (Mic, Screen Recording) are gated at launch via SetupWindowController -- don't add scattered permission requests elsewhere. Optional permissions (Calendar, Notifications) are accessible in Settings.
13. `EKEventStore.authorizationStatus(for:)` may return stale values within a session -- don't use `checkAll()` from individual Grant buttons, only update the specific permission that was requested
14. Floating panels must NOT use `.hudWindow` styleMask -- it creates a legacy dark HUD appearance that ignores system appearance and Liquid Glass. Use `[.titled, .closable, .utilityWindow]` instead. `SetupWindowController` is a standard `NSWindow` (not a floating panel) and is correct as-is.
15. USB webcam mics (e.g. Logitech C920) may deliver Int16 samples instead of Float32, and stereo instead of mono -- always detect format and channel count from CMSampleBuffer format description, never assume Float32 mono
16. AVAudioEngine cannot handle USB webcam mics -- fails with -10868 (kAudioUnitErr_FormatNotSupported) due to internal audio graph format negotiation. Use AVCaptureSession instead.
17. CADefaultDeviceAggregate is a virtual CoreAudio device -- filter it from device lists (`uniqueID.contains("Aggregate")`) to avoid hangs
18. `SCStreamConfiguration.microphoneCaptureDeviceID` (macOS 15+) overrides the default mic for ScreenCaptureKit capture -- set it to the AVCaptureDevice uniqueID
19. Ad-hoc re-signing invalidates TCC grants -- always reset TCC permissions after a fresh **ad-hoc** build. NOTE: no longer true once signed with the stable self-signed identity (see #57) -- then TCC grants persist across rebuilds/updates and must NOT be reset. `package_app.sh` uses the stable identity when present, ad-hoc otherwise.
20. **macOS 26 Liquid Glass panels (requires macOS 26.0+):** Floating panels use `panel.isOpaque = false` + `panel.backgroundColor = .clear` + `hostingView.layer?.backgroundColor = .clear`. Apply `.glassEffect(in: .rect(...))` as a **view modifier** on the content (not on a background shape -- `.glassEffect()` on a shape defaults to capsule/oval). Use `GlassBackgroundModifier` for consistent glass with `.regularMaterial` fallback on macOS 15. Top corners use 0 radius to sit flush against the title bar.
21. **NSPanel `hidesOnDeactivate`:** Defaults to `true` -- panels disappear when the menu bar app loses focus. Always set `panel.hidesOnDeactivate = false` on floating panels (SessionName, Rename).
22. **Engine model downloads (airgap guarantee):** ALL models (ASR ~500MB + diarization ~10MB) are downloaded eagerly during Setup or Settings Save -- NEVER at recording/transcription time. `ensureLoaded()` in both `FluidAudioEngine` and `FluidAudioDiarizer` will throw `FluidAudioEngineError.modelNotDownloaded` if cache is missing rather than silently downloading. Use `FluidAudioEngine.isModelCached()` and `FluidAudioDiarizer.isDiarizationCached()` to check cache; `preDownloadModel(progress:)` and `preDownloadModels()` to trigger downloads. SpeechAnalyzer uses the system framework (no download).
23. **SpeechAnalyzerEngine needs the macOS 26 SDK:** `SpeechAnalyzer`/`SpeechTranscriber` exist only in the macOS 26 SDK (Swift 6.2+). CI and development both build with it (#297), so there is no compile-time guard any more: the engine is `@available(macOS 26.0, *)` and every caller checks `#available(macOS 26.0, *)` at run time, because the deployment target is still macOS 15. Never reintroduce a `#if compiler(...)` branch (`ToolchainGuardTests` fails on one).
24. **FluidAudio decoder state (v0.14+):** `AsrManager.transcribe()` no longer takes a `source:` parameter -- caller manages `TdtDecoderState` directly via `inout`. In v0.13 the SDK kept two internal states (mic/system) keyed by source; in v0.14 it's exposed: `var s = try TdtDecoderState(); try await mgr.transcribe(url, decoderState: &s, language: nil)`. The state was never about audio preprocessing -- only TDT decoder LSTM hidden/cell + last-token continuity. For one-shot file transcribes a fresh state per call is fine; for chunked recording, holding a single state across same-source chunks preserves cross-chunk context (we currently use fresh state per call).
25. **FluidAudio ITN:** `TextNormalizer` converts spoken numbers to written form (e.g. "three hundred" -> "300"). Uses a native C library via `dlsym` -- gracefully no-ops if unavailable (`isNativeAvailable`). Applied per-segment after token grouping.
26. **Decimal-point sentence splitting:** The token grouper must not split on `.` when the next token starts with a digit (e.g. "1.5 million"), or it creates broken segments.
27. **Config default engine:** Must use `.resolvedDefault` (not `.speechAnalyzer`) so fresh installs on macOS 15 get FluidAudio instead of an unavailable engine.
28. **CLI entry detection:** Check for known subcommands (`transcribe`, `rename`, `benchmark`) not just `arguments.count > 1` -- LaunchServices can inject extra arguments.
29. **Crash recovery sentinel:** `~/Library/Application Support/Parley/recording.json` is written on recording start, deleted on clean stop. If it exists on launch, a crash happened. Check `RecordingSentinel.read()` and compare `startedAt` with system boot time to detect stale sentinels from a previous boot.
30. **LaunchAgent lifecycle:** `LaunchAgentManager.install()` on first launch, `LaunchAgentManager.uninstall()` before `NSApplication.terminate()` on explicit quit. Forgetting to unload means macOS restarts the app after every quit.
31. **XPC shared service instance:** `main.swift` uses a single `AudioCaptureService()` shared across all connections so a reconnecting client re-attaches to the same live session. Don't create per-connection instances.
32. **Multi-segment file naming:** Crash recovery creates segment files as `base-2.wav`, `base-3.wav`. Use `segmentBaseName()` from `SegmentNaming.swift` to strip/append segment suffixes -- don't inline the regex.
33. **WAV periodic sync:** `WavFileWriter` calls `synchronizeFile()` every 0.5s. Without this, a crash could lose up to ~30s of buffered audio. The sync is cheap (~0.05ms on SSD).
34. **Recovery runs before permissions gate:** In `TranscriberApp.init()`, the recovery Task must be launched before the permissions check. Recording must resume even while the permission setup window is shown.
35. **Stereo AAC channel convention:** L=local microphone, R=remote system audio. This is the contract between AudioArchiver (producer) and AudioSourceResolver (consumer). Never swap channels.
36. **System audio capture rate:** Hardcoded to 48 kHz in SCStreamConfiguration. The `sample_rate` config field is deprecated -- log a warning if present.
37. **Audio archive quota:** Enforced in hours via static calculation (hours x bitrate -> bytes). Only .m4a files count toward quota. Transcripts are never deleted. The just-archived file is always protected from cleanup.
38. **WAV is transient — everything flushes to .m4a:** WAV is only a crash-resiliency format used *during* recording. In the success path **every** finalized chunk is archived to AAC `.m4a` and its WAV(s) deleted — including single-stream (no-mic) chunks (`AudioArchiver.archiveSystemOnly`, #59) and single-chunk recordings. The source WAV is kept **only** when archival genuinely fails (encode/verify throws): deleting a WAV with no `.m4a` replacement would be real data loss. So: delete a WAV only after a verified `.m4a` exists (non-empty file with at least one audio track).
39. **Meeting summary fire-and-forget:** Auto-summary runs in a detached task after transcript write. Failures are logged but never block the pipeline or surface to the user. The summary is a derivative -- the transcript is the canonical artifact.
40. **Summary provider protocol:** `SummaryProvider` takes segments + metadata (not a pre-formatted prompt). Each provider owns its own prompt strategy. This allows Apple Intelligence to use a fundamentally different API shape.
41. **Two summary providers:** `OpenAISummaryProvider` uses `/v1/chat/completions` (standard, works everywhere). `LMStudioSummaryProvider` uses `/api/v1/chat` (LM Studio native: per-request context_length, token stats, MCP support). Selected via `config.summary.provider` ("openai" or "lmstudio").
42. **LM Studio context auto-sizing:** `LMStudioSummaryProvider` estimates input tokens from text length using a calibrated chars-per-token ratio, adds a 1024-token output buffer, and sets `context_length` per request. No need to pre-configure context in the LM Studio GUI.
43. **Token ratio calibration lifecycle:** On first encounter with a model, a transcript-style probe (~283 chars) is sent to measure the chars/token ratio (stored as "seed" in `~/Library/Application Support/Parley/token-ratios.json`). The first real transcript (>2000 chars) replaces the seed entirely with an exact measurement. Subsequent transcripts refine via EMA (0.3 new + 0.7 cached). The ratio is per-model (tokenizer property), not per-prompt.
44. **Token ratio self-correction:** If a context overflow error occurs (HTTP 500, `n_keep: N >= n_ctx: M`), the actual token count `N` is parsed from the error message, the exact ratio is set via `setRatio`, and the request is retried once with the correct context window. After self-correction the ratio is cached as a real measurement.
45. **CLI subcommand detection:** The `cliSubcommands` set in `TranscriberApp.swift` must include all CLI subcommands (transcribe, rename, rename-gui, benchmark, summarize). Missing entries cause the bare binary to fall through to the SwiftUI `@main` entry and crash on `UNUserNotificationCenter` (no bundle).
46. **Echo deduplication is a cluster verdict on time and text; the voice embedding is evidence, never a veto (rewritten for #242):** A local segment MATCHES when an unflagged remote segment of any remote speaker overlaps it in time (>50% of the shorter one) and repeats its words (Jaccard or containment >70%, or the Jaccard against the overlapping remote segments joined). A local cluster (speaker label, per chunk) is echo when at least 50% of its duration is matched and it holds at least 30 s: then every matched segment is flagged `echo`, and the unmatched ones stay unflagged under the cluster's label. Outside an echo cluster a match is flagged only from 3 words, so "Yes." said on both sides at once is kept. The earlier rule also required the cluster's speaker embedding to score >0.8 against a remote speaker, and that gate was all-or-nothing per cluster: on a real speaker-mode call the bleed cluster scored 0.68, so 0 of its 146 segments were flagged while 91% of its duration matched remote speech (the user's own cluster: 5% at most). Do not bring an embedding gate back, not even as a tie-breaker: laptop speakers into a far-field mic shift the voice, and bleed that minority absorption folded into the user's cluster carries the USER's embedding. The similarity is still computed and written (`metadata.echo_clusters[].embedding_similarity`); `echo_embedding_threshold` is accepted and ignored. The numbers behind every verdict are in `metadata.echo_clusters`, the flagged count in `echo_segments_flagged` (`echo_segments_removed` is the old name, written for one more release), and each chunk records `echo_flagged` / `echo_cluster` issues. Flagged, never deleted: the segment stays in the JSON and is hidden from TXT, SRT, the summary prompt and the rename samples; the raw audio archive is never modified. Thresholds in config.json: `echo_temporal_threshold`, `echo_text_threshold`; the cluster numbers (0.5, 30 s, 3 words) are constants.
47. **Speaker database key mapping:** FluidAudio diarization produces raw speaker IDs ("S2", "S3") but SpeakerAssignment maps them to friendly names ("Speaker 1", "Speaker 2"). The speaker database keys must be remapped using `SpeakerAssignment.remapDatabaseKeys()` before passing to EchoDeduplicator, or the embedding lookup will fail silently.
48. **Mic bleed mislabeling (known limitation):** When the mic picks up the remote speaker's voice, the diarizer may label the bleed + real local speech as one speaker in one segment. The dedup correctly preserves these mixed segments (text diverges from remote), but the local speaker's words get attributed to the wrong speaker. Fixing requires AEC (#35) to clean the mic channel before diarization.
49. **XPC crash detection requires `interruptionHandler`:** NSXPC's `invalidationHandler` does NOT reliably fire when an embedded XPC service crashes — macOS considers the service restartable and only delivers `interruptionHandler`. Both handlers must be installed on the connection, with a `crashHandlerFired` guard to prevent double-invocation. See `AudioCaptureClient.connect()`. *(The `crashHandlerFired` latch is gone: it survived a helper idle-exit and disabled crash detection for the rest of the app's life (gotcha #74). `XPCInterruptionPolicy` now arms detection per capture generation and fires at most once per generation.)*
50. **XPC crash retry limit must check before restart, not in catch:** `captureClient.start()` succeeds even when the XPC will crash on first audio sample (the crash happens asynchronously in the audio callback). The retry limit check must be at the top of the crash handler, before calling `start()`, not in the `catch` block.
51. **`.critical` notification entitlement:** `UNNotificationContent.interruptionLevel = .critical` requires the `com.apple.developer.usernotifications.critical-alerts` entitlement, which only works with a real Apple Developer signing identity — ad-hoc signing causes launchd to reject the binary (error 163). Use a floating NSPanel as fallback. Entitlements file ready at `packaging/Parley.entitlements`.
52. **Testing XPC crash resilience:** To inject a crash in the XPC service, add to `AudioOutputHandler.handleMicAudio()`: a `#if DEBUG` block that checks for `~/Library/Application Support/Parley/CRASH_TEST` file existence (via static lazy `Bool`), and calls `fatalError()` on first mic sample if present. Use `micCrashInjected` instance flag to crash only once per XPC process. `touch ~/Library/Application Support/Parley/CRASH_TEST` to arm, `rm` to disarm. Expected: crash #1 → retry, crash #2 → retry, crash #3 → criticalError + floating panel.
53. **Model manifests track HF commit identity:** Every successful Parakeet download writes `~/Library/Application Support/Parley/model-manifests/FluidInference_parakeet-tdt-0.6b-v3-coreml.json` capturing the HF top-level commit SHA + per-file SHA-256. The FluidAudio cache itself is filename-keyed and never re-pulls if files exist, so the manifest is the only record of *which* model version is on disk. Local verification runs on launch (cheap, offline). Online "is HF newer" check is opt-in via Settings -> Model Updates and never downloads automatically. The opt-in flag is `Config.modelUpdateCheckEnabled` (default false, JSON key `model_update_check_enabled`).
54. **LaunchAgent KeepAlive double-launch — the dict form does NOT prevent it (corrected, #109):** An earlier note here claimed the dict form `KeepAlive={SuccessfulExit:false}` (vs boolean `<true/>`) stops `launchctl load -w` from spawning a duplicate. **That is wrong** — device-confirmed that launchd starts a KeepAlive job at load time regardless of the dict-vs-boolean form (the dict only scopes *restart-after-exit*, not the initial launch-on-load). So loading the agent from inside the running app spawns a second instance (two menu-bar icons; `launchctl list` shows both `application.eu.fmasi.parley.<n>` and `eu.fmasi.parley`). The real fix is a **single-instance guard** (`SingleInstanceGuard.acquireLock` + `TranscriberApp.yieldIfDuplicateInstance()`) built on a **kernel `flock`**, NOT an `NSRunningApplication` scan. The first guard version *did* scan the running-app list (oldest instance wins) and **still double-launched on device (confirmed 2026-07-02)**: a launchd-spawned duplicate runs its check inside `App.init()`, before the first instance has registered with LaunchServices, so the scan returns an empty peer list and BOTH instances survive (`launchctl list` shows both `application.eu.fmasi.parley.<n>` and `eu.fmasi.parley`; two Setup windows). A `flock` is atomic in the kernel and independent of app registration, so exactly one instance acquires it and the duplicate exits cleanly with status 0, which `SuccessfulExit:false` will not relaunch, so exactly one instance survives. The lock (`~/Library/Application Support/Parley/instance.lock`) releases automatically when the holder exits — crash included — so a crash-recovery relaunch re-acquires it. The dict form is still correct for its actual purpose (scoping crash-recovery relaunch to abnormal exits) — it just never prevented the double-launch. Guard logic is unit-tested in `SingleInstanceGuardTests`.
55. **AVCaptureDevice disconnect notifications don't fire for audio input on macOS:** `AVCaptureDevice.wasDisconnectedNotification`, KVO on `AVCaptureDevice.isConnected`, and `AVCaptureSession.runtimeErrorNotification` are camera-oriented and do NOT fire when a Bluetooth/USB **audio input** device is removed mid-capture (e.g. AirPods put in the case) — the `AVCaptureSession` just silently stops delivering sample buffers (the mic WAV ends early, no error). `AVAudioSession.routeChangeNotification` (the iOS idiom) is unavailable on native macOS (Mac Catalyst only). The native mechanism is a Core Audio HAL property listener: `AudioObjectAddPropertyListenerBlock` on `kAudioObjectSystemObject` for `kAudioHardwarePropertyDevices` and `kAudioHardwarePropertyDefaultInputDevice` (fires within ms, needs no microphone TCC). Do NOT use a no-buffer polling watchdog. See `docs/mic-capture-design.md`. (Confirmed by device test 2026-06-26 + Apple Dev Forums 766106.)
56. **New speaker appearing mid-recording gets a continued "Speaker N" label (#113):** `SpeakerReconciler.reconcileNamespace` seeds its reference embeddings from the first chunk. A speaker with no cosine match against those seeds (only possible in 3+ person calls, or if the diarizer keys speakers inconsistently across chunks) is minted a fresh global label that **continues the friendly numbering** — e.g. `Remote Speaker 3` — rather than the raw internal `spk_N` it used to leak (the old `nextGlobalIndex` parse split on `_`, which never matched the production `"Speaker N"` labels, so the counter stayed at 0 and minted `spk_0`). `trailingIndex()` now parses both the space- and underscore-separated forms, so the counter stays above every in-use index and minted labels never collide. If you see `Remote Speaker N` for someone who first spoke partway through a long recording, that's the reconciler being honest that they weren't in the seed chunk — expected, not a regression.

57. **Stable self-signed identity so TCC survives Sparkle updates (#114.3):** TCC binds each permission grant (Microphone, Screen Recording, Calendar) to the app's *designated requirement*, derived from the code signature. Ad-hoc signing (`codesign --sign -`) mints a fresh cdhash every build with no stable identity, so macOS treats every Sparkle update as a new app and drops all grants — the user must then remove + re-add Parley per-permission in System Settings (Screen Recording can't even be re-prompted programmatically). Fix: a stable self-signed cert (`scripts/setup-signing-cert.sh`) pins the DR to `identifier "eu.fmasi.parley" and certificate leaf H"…"`, constant across rebuilds, so TCC re-matches the update and keeps the grants. Gotchas that bit us: (a) OpenSSL 3.x (Homebrew/conda) writes a PKCS12 whose MAC Apple's `security import` rejects — use the system LibreSSL (`/usr/bin/openssl`); (b) a self-signed cert is `CSSMERR_TP_NOT_TRUSTED` and `codesign` refuses it until `security add-trusted-cert -p codeSign` trusts it, which triggers a one-time GUI password prompt (can't be fully headless); (c) the first build after switching off ad-hoc changes the identity once, so that single update still re-prompts — persistence holds from then on. Sparkle also *requires* the update be signed with the same identity as the installed app, so stable signing hardens the update path too. Full Developer ID (paid) is the eventual upgrade — it adds notarization (no Gatekeeper first-launch friction) and the `.critical` alert entitlement (#51). End-to-end update path validated via `scripts/sparkle-dryrun.sh`.

58. **Never clock the capture aggregate off a Bluetooth device — its rate at build time predicts nothing (2026-08-04):** A Bluetooth output flips A2DP→HFP (48 kHz→24 kHz) *whenever something opens its microphone* — which is exactly what recording a call does. That profile switch is **not** a device change, so no `kAudioHardwarePropertyDefaultOutputDevice` listener fires and nothing rebuilds; the IOProc keeps converting against the stale 48 kHz format, ~half the frames arrive, and `WavFileWriter` pads silence to hold the wall clock. Result: **correct duration, corrupt content** — 2x-fast (chipmunk) speech interleaved with gaps, which still transcribes into plausible-looking but wrong text (a real session transcribed the company "Harvey" as "Robbie"). The #111/#112 fix read the *aggregate input stream* format instead of the tap format, which was necessary but not sufficient: it is a point-in-time read that **races the HFP transition**. Device-confirmed 2026-08-04 — AirPods connected mid-meeting, the rebuild read them as 48 kHz (still A2DP), anchored to them, and macOS dropped them to 24 kHz ~5 s later; 22 of 24 minutes were captured chipmunked. The fix is transport-based, not rate-based (`ClockAnchorPolicy`): never anchor to a Bluetooth device whatever rate it currently reports, and treat a measured drift as a *trigger to rebuild*, not just something to log. Detection alone is worthless here — the watchdog fired 5 s in and the remaining 22 minutes were still written wrong. **Rescue for an already-corrupted file is lossless:** the samples are intact and only the declared rate is wrong, so rewriting the WAV header rate (48000→24000, no resampling) restores correct pitch; wall-clock timestamps map back as `t_true = t_rescued / 2` because the corrupted file was wall-clock anchored.

59. **Interleaved `AVAudioPCMBuffer`s do NOT have nil `floatChannelData` — never branch on the accessor to detect layout:** An interleaved buffer exposes a *single interleaved plane* through `floatChannelData[0]` (stride = channel count), so `if let channelData = pcmBuffer.floatChannelData { … } else { /* interleaved path */ }` sends interleaved buffers down the **planar** branch and the interleaved branch becomes dead code. That bit us in the mic path: the copy was clamped to `frameLength * MemoryLayout<Float>.size` with no `* channelCount`, so any **stereo** mic (USB interface, some webcams — `MicCaptureSession` sets no `audioSettings`, so the device's native format is used) had exactly **half of every buffer dropped**, leaving the destination tail zeroed. Correct duration, choppy content, no error anywhere — the same silent-divergence class as #58, introduced by the clamp that was added to fix a genuine heap overrun (#94). Branch on `format.isInterleaved`, take the sample width from `streamDescription.pointee.mBitsPerChannel` rather than inferring it from which accessor is non-nil, and derive `frameLength` from the bytes actually copied (a short buffer after a route change otherwise leaves an uninitialised tail that converts to a noise blip, not the silence it resembles). Byte math lives in `PCMCopyPlan` (unit-tested).

60. **`AVAudioFile.read(into:)` does NOT resample and does NOT throw on a format mismatch — it raw-copies frames:** Apple's docs say the buffer's format must match the file's `processingFormat`; that is enforced as *nothing*. Reading a 24 kHz file into a 48 kHz-declared buffer returns bit-identical samples to a correct read, silently. `AudioArchiver` took its encode rate from the **mic** file and never consulted the system file's, so a rate-divergent pair (a #58-rescued file re-ingested, or an early-crash orphan carrying `WavFileWriter`'s 16000 Hz fallback header) encoded "successfully" into a structurally perfect `.m4a` — system channel pitch-shifted and half-length — which then passed verification and **both source WAVs were deleted**. Irreversible: the lossless header-rewrite rescue needs the original WAV. Two lessons: (a) assert both streams' rates agree before encoding and refuse otherwise, and (b) "verified" in gotcha #38 must mean *duration compared against the sources*, not merely "file is non-empty and has a track" — a truncated encode satisfies the weak check perfectly, and the check exists solely to license deleting the only lossless copy.

61. **Pad ratio is the mechanism-independent tripwire for silent capture corruption:** `timelineSilencePad` inserts silence so each track's next sample lands at its true wall-clock position — correct, and how mic/system stay aligned across start skew and restart gaps. But it also means that when a device *under-delivers*, the padder quietly makes up the difference and converts a detectably-short file into an undetectably-corrupt one of exactly the right duration. That is what hid #58 for 22 minutes. The saving grace: padding only ever responds to **delivery deficit**, never to quiet audio (a silent remote still delivers buffers of zeros and pads nothing), so the ratio separates cleanly — measured **61.1% on the corrupted track vs 0.1% on the healthy mic in the same recording**, across 56,737 discrete zero-runs averaging 15.6 ms (the per-buffer catch-up signature). Legitimate padding in a real meeting is ~0.1–3%, so a 10% threshold sits an order of magnitude clear of both. `PadRatioMonitor` requires BOTH a high ratio and an absolute floor of fabricated seconds — a ratio alone fires on ordinary start-of-meeting gaps (one 4 s gap evaluated at the 30 s mark reads 13%, and 4 s gaps happen whenever a Bluetooth mic negotiates HFP or an #86 restart's first liveness probe misses), and a detector that cries wolf is worse than none. It accumulates per track per CHUNK — the timeline anchor and frame counters are chunk-scoped, so accumulating across rotations would mix anchors — and reports **once** per chunk (the original per-buffer pad log fired ~57,000 times at `.info` and told nobody anything). Because it measures the *symptom* rather than any particular cause, it catches this bug class in mechanisms nobody has thought of yet — which is the only kind of guard worth having here.

62. **A recording the app knows is compromised must not present as clean:** the capture layer detected #58 at t≈5s and stamped it into `capture_provenance` and `.diag.jsonl` — then `presentCompletedTranscription` posted an unconditional "Transcription Complete" and opened the rename dialog exactly as for a clean recording. For a tool whose purpose is a courtroom-grade record, filing an exhibit the system already knows is tainted, unlabelled, is worse than never having detected it: the knowledge existed and nothing carried it to the human. `CaptureQualityNotice` reads `metadata.capture_provenance.quality_anomaly_count` back off the finished artifact — deliberately NOT the raw `anomaly_count`, which includes `.streamStopError` recorded for a benign Bluetooth A2DP↔HFP route change. Since opening the mic is what triggers that flip, it fires on nearly every recording made on the default (SCK) source with wireless headphones, and counting it would brand healthy recordings as suspect and destroy the signal on arrival. `CaptureEventKind.qualityCompromising` is the filtered set: only anomalies that survive recovery — deliberately re-reading the file rather than threading state through call sites, so the crash-recovery and salvage paths (where compromised captures are most likely and least examined) get the same treatment for free.

63. **Liveness must mean "we are recording", not "the OS is still calling us":** the #86 restart probe read a timestamp stamped on *every* arriving system buffer — including buffers the sticky format gate then dropped. A stream whose buffers were all being discarded therefore looked perfectly alive: the probe saw fresh arrivals, concluded frames had resumed, reset its restart budget, and blessed a stream writing nothing to disk. The stamp now sits **after** the gate, so only a buffer we can actually write counts as life. A muted remote is still counted alive, because muted audio passes the gate — only writer-*incompatible* buffers are excluded. Sustained drops now also record an anomaly rather than vanishing silently.

64. **A non-default clock anchor needs its own device-list listener:** `SystemTapSession` watched only `kAudioHardwarePropertyDefaultOutputDevice`. Once re-anchoring became common (any Bluetooth or virtual default output sends the clock elsewhere), the anchor is routinely a device the user never selected — and unplugging *that* fires no default-output notification. The IOProc then stalls forever, and a stall is invisible to `RateDriftMonitor` because that watchdog only runs when buffers arrive: zero callbacks means zero detection. The system track simply stops growing while the mic keeps recording and finalize reports success. Fixed by mirroring what `MicCaptureSession` has always done (gotcha #55): a second listener on `kAudioHardwarePropertyDevices` that rebuilds when the *anchor's* UID disappears — checked by UID, so unrelated device churn doesn't tear a hole in every recording.

65. **An empty WAV header declares a sample rate that means nothing — treat zero frames as "no stream", not "a stream at 16 kHz" (#183):** when a capture opens a WAV and never writes a frame, the file is a valid 44-byte header reporting a nominal **16000 Hz** and zero frames. That happens routinely on a mic-only recording — a phone call answered and put on speakerphone — because there is no system audio to capture at all. `AudioArchiver.archive` compared that nominal 16 kHz against the mic's real 48 kHz, hit the rate-mismatch guard (correctly added to stop a genuine divergence raw-copying a pitch-shifted channel and then deleting both lossless sources), and refused. The recording then never archived, and — because `ChunkProcessor` records the SYSTEM wav as the chunk's `audioPath` on archive failure — the transcript pointed at the empty header while the mic WAV holding every word was referenced nowhere. `SpeakerSampleLocator` resolved `local: nil`, every segment was `source: "local"`, and the rename dialog drew no play button. Device-observed twice, on 2026-07-16 and 2026-09-02: both a phone call answered and put on speaker. Guard on `AVAudioFile.length > 0`, never on the declared rate. And note that a mic-only archive needs its **own** path: `archiveSystemOnly` fills the RIGHT channel, so reusing it for mic audio puts the local speaker in the remote slot and mislabels them everywhere downstream — the gotcha #132 class of harm, silently.

66. **The Core Audio tap delivers NO buffers while the output device is idle — so leading silence is pure padding, and a pad-ratio detector must ignore it (2026-08-11):** Unlike ScreenCaptureKit (whose stream keeps delivering zero-filled buffers, which is what the #86 liveness probe relies on), the tap's IOProc only runs while something holds the output device open. Start a recording *before* joining the call — the ordinary way to use the app — and the system track receives nothing until the call connects, so `timelineSilencePad` fabricates the entire span. Device-observed on the first real firing of `excessivePadding`: a perfectly healthy 30-minute recording measured **97.6% zero samples in its first 30s** (2.8% from 60-300s, 4.2% overall) and tripped the detector at ratio 0.911 with 27s of padding — clearing both the 10% ratio threshold and the 15s absolute floor, because leading silence trivially exceeds any absolute floor. The fix is not a bigger threshold but the right distinction: **padding before a track has ever delivered a frame is a START OFFSET, not a deficit** — nothing went missing because there was nothing to capture. `PadRatioMonitor` therefore accumulates nothing until its first `dataFrames > 0`. This preserves the #58 detection exactly, because in a genuine rate drift the device IS delivering (a call is connected, silence still arrives as zero-filled buffers at the wrong rate) — the monitor simply starts when the frames do.

67. **A `URLError` from a summary provider is not a file error — map it explicitly (2026-08-11):** `MeetingSummarizer.runSummary`'s catch-all assumed "non-`SummaryError` ⇒ file read/write failure" and reported *"Couldn't read the transcript or write the summary — check disk space and permissions"*. `URLError` is not a `SummaryError`, so a request timeout landed there and told the user to check permissions. That misdirection cost two separate debugging sessions (2026-08-04 and 2026-08-11) before the real cause — a `-1001` timeout against a local LM Studio that accepted the request and then generated for longer than the 60s stock `URLSession` timeout — was found in the unified log. Two lessons: catch `URLError` before any catch-all that assigns a *cause*, and never let a stock network timeout govern a LOCAL model (a long transcript routinely needs minutes). `SummaryConfig.requestTimeoutSeconds` now defaults to 600s. The same lesson applies one level down: a bare `HTTP 401: <body>` is technically accurate and practically useless, so 401/403 is classified as `SummaryError.authenticationFailed` with a message naming the API key — and deliberately WITHOUT the response body, because some servers echo the offending credential back and this text reaches a notification that can be on screen during a shared meeting (the same reason `invalidEndpoint` is sanitized). Rule of thumb for this whole surface: a failure message should name the thing the user must change, and nothing else.

68. **`AVCaptureSession.startRunning()` blocks — never call it on the main thread, and design for it never returning (#192, 2026-09-10):** the level meter in `MicrophonePicker` (shared by the session-name dialog and the mid-recording mic switcher) started its own `AVCaptureSession` from `.onAppear` — on main — and called `startRunning()` synchronously. Before recording nothing else holds the mic, so it always returned, which is why it "worked" for months. Mid-recording, the capture helper already runs that microphone's IO, and the second `startRunning()` waited on a CoreAudio HAL lock (`HALB_IOThread::StartAndWaitForState` → `HALB_Guard::WaitFor` → `__psynch_mutexwait`) and **never returned**, freezing the UI permanently. `stopRunning()` has the same shape. The capture helper's `MicCaptureSession` already did this correctly — both calls on a dedicated serial `configQueue` — and the level meter simply never adopted the pattern. Rule: every AVCaptureSession lifecycle call goes on a background queue, one queue **per session**, so a session whose start never returns wedges only itself and the user can still switch to another device. Observed with the lid closed (built-in mic hardware-disabled); whether an open-lid mic hangs the same way is unverified, and the fix does not depend on it. If a freeze like this ever recurs, the capture helper is unaffected: quitting the frozen app makes the helper finalize the WAVs on XPC disconnect, and relaunch recovery transcribes them. Three corollaries, from the fix's review: (1) a level meter must **never open the mic the recording holds** — `RecordingMicrophone` records it and the meter shows "In use" instead, compared by *physical* device (System Default and the default mic's own entry are one device); (2) a dialog must **release its meter and wait (bounded) before the helper opens the mic** it was showing — `InputLevelMonitor.stopAndRelease(timeout:)`; (3) `AVCaptureDevice.DiscoverySession` reads the same HAL, so the device list is scanned in the background too (`AudioDeviceCatalog`) — it used to run in the menu's `body` on every timer tick.

69. **A fresh `EKEventStore` per call is a deliberate, accepted tradeoff — not an oversight (#197, 2026-09-18):** Apple's EventKit docs say to create one event store per application and reuse it, not one per call. `CalendarService.currentEventTitle` creates a new `EKEventStore()` inside its background dispatch closure on every "Start Recording" tap instead, because `EKCalendar`/`EKEventStore` thread-safety across actor/queue boundaries is unspecified, and a fresh, queue-local store sidesteps that entirely. The accepted cost: `EKEventStore()` isn't actually cheap — it's a Core Data stack bring-up, ~50–200ms, worse on Exchange/LDAP accounts — paid on every panel open. Tolerable because the lookup runs once per Start Recording, not a hot path. If Exchange/LDAP accounts ever show symptoms of repeated store creation (stale/inconsistent event data, redundant auth/sync churn), the fix is a dedicated actor holding one retained store (all EventKit calls isolated to its executor), not a shared instance property — see the `TODO` in `CalendarService.swift`.

70. **The Core Audio tap's System Audio Recording permission belongs to the HOST APP, and without it the tap records digital zeros, silently (#220, 2026-09-23):** A real 52-minute call recorded the local side perfectly and captured **no** remote audio: the archive's system channel was exact digital zero from t=0. Without `kTCCServiceAudioCapture`, `AudioHardwareCreateProcessTap`, the aggregate and `AudioDeviceStart` all return `noErr` and the IOProc fires at full rate, delivering zeros. The only trace is `coreaudiod` logging `HALS_IOContext.cpp:1508 Client is not granted access to the tap.` (error level, so it survives in `log show` for ~14 days, which is how this was found). A device spike (a throwaway app + XPC helper mirroring Parley's layout) established four facts: (a) **TCC attributes the helper's tap to the host app.** The prompt names the app and shows the *app's* `NSAudioCaptureUsageDescription`; a copy only in the helper's plist (as #106's review round 2 had moved it, reasoning that grants are keyed to the calling bundle) means macOS **never prompts** and the status stays "not determined" forever. (b) A grant takes effect in an already-running helper: rebuilding the tap is enough. (c) `TCCAccessPreflight` caches its answer **per process for the process lifetime, in both directions**: the long-running app kept its launch-time answer after a grant *and* after a revocation, while the helper, which touches the tap, saw both. So live checks go through the helper over XPC. (d) There is no public API for this permission; Parley uses the private `TCCAccessPreflight`/`TCCAccessRequest` via `dlsym` (see `docs/app-store-blockers.md`). The fix: the usage string in the app plist, a helper check at tap start, an exact-zero-run detector on tap samples that triggers a permission check (never an alarm on its own, since a silent call can be exact zeros too), and the repair window. Also: holding **Screen Recording** does not help the tap. It's a separate permission, listed separately in System Settings under "System Audio Recording Only".

71. **A track that never delivers looks exactly like one that has not started yet (Incident B, 2026-09-24):** every detector was either driven from inside the audio callback (rate drift, pad ratio) or refused to judge `lastArrival == 0`. Stamp a heartbeat at the TOP of the callback and judge "expected but silent" from the moment capture/rebuild/wake armed the monitor — `TrackLivenessMonitor`. "Expected" for the tap means "some OTHER process is running output", never "the default output device is busy". Both clocks count only time during which the gate was open.

72. **`kAudioProcessPropertyIsRunningOutput` is IO state, not content, and includes us:** a process rendering exact digital zeros reads 1 until it exits, and the helper's own capture aggregate reports itself as running output on its anchor device. Exclude `getpid()`, or the gate holds itself open forever. Fail OPEN on a read failure.

73. **The HAL can pause an aggregate's IO after a successful `AudioDeviceStart` and never resume it, with no callback:** Incident B's context was started/stopped three times by a config-change sweep on the anchor (triggered by the helper's own mic opening on AirPods HFP, not by the call app), ended in `PauseIO` count 1, and `StartAndWaitForState` failed with EAGAIN inside the HAL client. `AudioDeviceStart` had returned `noErr`. `stpd`/`goin` listeners are accelerators; the heartbeat decides; the fix is a new IO context (aggregate rebuild), then a new tap. Every rebuild carries a token so an output-device rebuild finishing mid-rung is never mistaken for the rung's result.

74. **launchd idle-exits the embedded XPC helper ~10 min after its last message, and that interruption is not a crash:** the old `crashHandlerFired` latch treated it as "handled" and was reset only in `connect()`, so every real crash after that ran no recovery. Arm crash detection per capture generation (`XPCInterruptionPolicy`); never ping the helper while idle (the ping spawns a throwaway helper).

75. **`launchctl unload` from a launchd-spawned instance SIGTERMs the process before the plist removal runs — the plist survives and `isInstalled()` lies:** remove the plist FIRST, then `bootout`. A plist on disk proves nothing; `launchctl print gui/<uid>/<label>` does. Verify and repair at every launch, and say so only when repair fails.

76. **`ProcessInfo.systemUptime` excludes sleep:** measured 7.2 h short after four days, so a sentinel from a recording that started during that window was "from before the last boot" and deleted. 77. **`AudioConcatenator` given a mono WAV among stereo AACs re-encodes the mono into BOTH channels and deletes it (probe-proven):** the remote voice lands in the local slot for every channel-splitting consumer, and the only lossless copy is gone. 78. **`kAudioAggregateDeviceTapAutoStartKey = true` defers `AudioDeviceStart` until a tapped process receives its first audio, and the HAL re-arms the autostart context after every IO stop.** Gotcha #66's leading silence is this key. Under `true`, "no callbacks" is ambiguous (idle or broken); under `false` the IOProc runs continuously and delivers zeros when idle. Which one ships is decided by measurement M-B (device checklist D-12); the setting is `tap_auto_start` and is stamped into `captureStart` provenance.

79. **A helper restart starts with an empty alarm registry; the app must not read that as "all clear":** the app keeps the previous helper's alarms as stale until the NEW helper disproves each one with matching evidence — first frames for a delivery kind, a non-zero sample for a content kind (a denied tap delivers frames on time, all of them zero), a successful write for `diskWriteFailure` — and never resets the 2-minute notify clock on a 5-second poll (`CaptureAlarmRegistry.apply` / `noteFirstFrames` / `noteRealAudio` / `noteWriteSucceeded`). The notify clock is per KIND and survives clears, so a flapping condition cannot notify faster than every 2 min.

80. **Helper session ids must be ORDERED, and ordered by a clock that never steps back:** keying the stale-alarm rule on "a different id" let a late message from a replaced helper adopt the dead helper again. The id is `"<ms>-<registryResets>"` where the ms come from `CLOCK_MONOTONIC` at process start (wall-clock ms would order a replacement started after an NTP step-back BEFORE the helper it replaced, and the app would ignore it for the rest of the recording) and the counter increments on every registry reset; the app adopts only a strictly newer id. Every snapshot carries a `sequence` taken in the same critical section as the alarm read. Never read the helper id getter inside that lock.

81. **A Finder/Sparkle-launched Parley is not the process launchd's `KeepAlive` tracks, so a crash of it is NOT relaunched — and `launchctl bootstrap` after an `unload -w` fails until `launchctl enable`:** `launchctl print gui/<uid>/eu.fmasi.parley` shows `pid =`; when it is not ours the app hands over (`launchctl kickstart -k` launchd's own copy, then exits 0) and the launchd copy — recognisable by `XPC_SERVICE_NAME == eu.fmasi.parley` in its environment — waits up to 10 s for the single-instance lock instead of yielding. 82. **A speaker label stored in the metadata is the label at the time it was written; a dialog row shows the current one (#244):** `echo_clusters[].label` and the keys of `matched_remote` are never rewritten by a rename, while the segments (and so the rename dialog's rows) carry the name. Matching one against the other by string finds nothing on a renamed transcript — the echo notice would vanish and the speaker count would include the echo voice again. Go through `metadata.speaker_names`, and follow it as a CHAIN: each rename is keyed by the label current at that moment (`Local Speaker 2 → A`, then `A → B`), and a rename there and back makes a loop. `EchoNotice.Findings` does this (`rowLabels(of:)`). Copy, on the other hand, names the stored label, not the name: the stored label is what the check compared.

83. **An IOProc created with `AudioDeviceCreateIOProcIDWithBlock` and a dispatch queue is dispatched SYNCHRONOUSLY, so the wait for that queue is inside the IO cycle; and `inInputTime` is not when the callback was called (#247):** `AudioHardware.h` says "All IOBlocks are dispatched synchronously": the HAL's IO thread blocks until the block returns. Anything else on that queue (the mic delegate, a file write, an `fsync`, a rotation's finalize) is therefore inside the tap's IO cycle, which `coreaudiod` judges against the device's budget (#247: `ClientHALIODurationExceededBudget`, 56.5 ms against 11.35 ms with ~0.5 ms of CPU; whether the queue is what it waited on is what `IOCycleStats` measures). To time the wait, use `inNow.mHostTime` ("the IO cycle started"), not `inInputTime.mHostTime`, which is when the buffer's FIRST frame was acquired from the hardware: a whole buffer (10.7 ms at 512 frames / 48 kHz) before the callback, so "entry minus `inInputTime`" reads as an overrun on every cycle. And close the measurement at the block's LAST statement: the first version closed the tap's cycle when `AudioOutputHandler` had written, while the service's sample closure still ran `TapPermissionGuard`'s pass over the buffer before returning to the HAL, so the system track's total stopped short of what `coreaudiod` budgets (and the mic's did not: its exact-zero scan ran before its cycle closed). A slow pass there would have read as "within budget" next to an overload (#259 review). The tap's closure now ends with `endSystemCycle`, and the span after the write is its own stage (`check`) on both tracks. The structural fix is #248.

84. **At `-Onone` (a DEBUG build: `python3 scripts/dev.py --debug-build`, `just build`, `bash package_app.sh` without `--release`, the test suite) code that is allocation-free when optimised is not (measured with a `malloc_logger` hook, #247):** (a) a generic iteration (`for i in 0..<n`, `for x in array`, `allSatisfy`, `contains(where:)`) costs one or two `malloc`/`free` pairs PER ELEMENT: the unspecialised `IndexingIterator.next()` reads the element through the `Collection.subscript.read` witness, a coroutine whose frame is heap-allocated; a `while` loop with an index does not. (b) A stored `static let` is initialised behind a once-token on its first read, which is then on the audio queue. (c) A large homogeneous tuple used as inline storage has its type metadata instantiated (a handful of allocations, once per process) the first time it reaches a generic function such as `withUnsafeMutableBytes(of:)`. `IOCycleStats` therefore has no generic loop on its record path, uses computed static constants, touches its storage once in `init`, and its allocation test loops with `while`. Consequences: the capture callbacks' own per-sample scans (`allSatisfy` in `ExactZeroRunMonitor`, `TapPermissionGuard` and `AudioOutputHandler`) allocate per sample in a debug build whenever a buffer is all zeros, so a timing taken on a debug build is not the shipped app's. Until #271 plain `dev.py` installed a debug build; it now installs a release build unless given `--debug-build`, and the helper writes `"build": "debug"` or `"release"` into each recording's `captureStart` event (`BuildConfiguration`). Say which build a measurement came from.

85. **The quota never deletes the audio of a session that still has state in its folder (#230):** two sessions can share a day folder (one recording, one being processed or awaiting salvage), and each quota pass used to protect only the files of the session that ran it, so it could delete the other's chunk archives: the only copy once the WAVs are gone. Before any delete, `StorageManager.enforceQuotaReport` now reads the candidate's folder once (`SessionState.sessionIdsWithState`: the ids stored in `session.json` and every `session-*.json`) and skips every `<id>.m4a` / `<id>-<n>.m4a` of those ids; nothing is read while usage is under the quota. Three consequences. (a) A finalize deletes its session file, which is what makes a finished session's audio deletable again; a session file that lingers keeps that session's audio, and the pass reports it as a protected overrun. (b) A session file whose id cannot be read keeps EVERY archive in that folder: it says a session has state there, not which; the log names that file, and the record's overrun says the folder is held by a session file Parley cannot read (#294). (c) A session id can start another (`a` and `a-2`: an id is a time plus the typed name), and `a-2.m4a` is then `a`'s chunk 2 or `a-2`'s merged file; the name cannot say which, so it is kept while either has state. A session's first `session.json` is written when its pipeline is set up, not with its first chunk (#294), so its first chunk's archive is protected too. So `session.json` no longer means "a chunk was saved": a session that ends with nothing to salvage (no chunk in its state, no chunk file on disk) removes its empty state on every path that ends it (`CrashRecoveryPlanner.removeEmptySessionState`, from the unsalvaged outcome of a Stop, a failure or a salvage, from a Stop with no live pipeline (a re-attached recording), and from a recovery that finds nothing); left, the next recording in the folder would move it aside, record a spurious `session_file_displaced`, and the copy would keep that id's archives for good. Fail-closed: state that holds a chunk or cannot be read, a chunk file on disk, or another session's file is kept and logged; a finalized session's state is left to its own cleanup (`cleanupFinalized`). The record's `quota_exceeded_by_current_session` issue keeps its raw value, but its `detail` says whose audio keeps the folder over: this recording's, another recording's still in flight (never its name: the record may be shared), a folder whose session state cannot be read, files that are not Parley recordings, or files that could not be deleted.

86. **`withDeadline` stops WAITING for its body; it does not stop the body (#226):** the Stop's wait for chunk processing is bounded, and when the bound runs out the chunk tasks are still running: hung in a file call on a folder that does not answer, or only slow. They finish later and still archive and persist their chunk. So nothing may re-read that session's files in the same process until they have ended: a salvage started meanwhile would build a second `ChunkProcessor` over the same WAVs, transcribe the chunk twice and have two archivers write the same `.m4a` (each removes "stale output" first). `RecordingCoordinator.chunksStillProcessing` holds the session out of `retryPendingSessions` until the tasks end, then retries; a relaunch has no such tasks and salvages at once. The same applies to any new bounded wait around work that writes files: say what happens to the work after the bound. Also: the ASR call, the header repair and the AAC encode are still unbounded themselves and pin a cooperative-pool thread each while the folder hangs.

87. **`URL.deletingLastPathComponent()` on the root does not answer the same thing on every OS, so "climb until the parent equals the current URL" may never end:** on current macOS (measured on 27.0.1) `URL(fileURLWithPath: "/").deletingLastPathComponent()` is `/` again, and a loop that stops when the parent equals the current URL stops there. The older, `NSURL`-backed implementation answers `/..`, then `/../..`, and so on: every parent is a different URL from the one before, the paths get longer, and the loop never ends. `NSURL` itself still answers `/..` on macOS 27 (`NSURL(fileURLWithPath: "/").deletingLastPathComponent`), so code that goes through it, or that runs on an OS where `URL` is still backed by it, meets the second answer. Do not compare for equality. Climb only while the parent's path is strictly SHORTER than the current one: `/` is not shorter than `/`, and `/..` is longer, so the walk ends at the root on both. That is `RecordingCoordinator.walkGoesUp(from:to:)` in `TranscriberCore/RecordingFolder.swift`, used by `nearestExistingDirectory`, which climbs from a recording folder that does not exist yet to the nearest ancestor that does (for the writability check and the free-space reads). The loop's other exit is "this folder exists", which a real `/` satisfies; with a probe that says nothing exists (a test's, or a file system that is not answering truthfully) the walk reaches the root's parent, and only the shorter-path rule ends it. `theWalkUpStopsAtTheRootWhateverItsParentIs` in `RecordingCoordinatorTests` builds both answers, so it fails on any Mac if the stop ever depends on which one the OS gives. The same applies to any walk up a path: a bound on the number of steps, or a path that must shrink, never "until it stops changing".

88. **FluidAudio's `OfflineDiarizationError` code 5 is `noSpeechDetected`, not `exportFailed` (#302):** a log line shows a Swift error bridged to `NSError` as `OfflineDiarizationError` and a code, and the code is not the case's place in the declaration.
